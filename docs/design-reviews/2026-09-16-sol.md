## Blunt assessment

Silent Regression has excellent evidence, audit, tenancy, and spend-control architecture wrapped around an evaluator whose actual product value is narrower than the workflow suggests.

The danger is false confidence: users complete a rigorous-looking setup, fixture approval, baseline capture, and review process, but the system may still be testing a materially different request from production and cannot determine whether many case-specific answers are correct.

## What is genuinely strong

I would preserve these decisions:

- Ledger-first provider calls and explicit unknown outcomes.
- Immutable monitor, contract, baseline, evaluation, and review history.
- Strict workspace scoping and owner/member boundaries.
- Separating operational anomalies from content conclusions.
- Honest rejection of unreliable “semantic drift” scoring.
- Local contract evaluation and historical rescoring without new provider spend.
- Explicit call limits, preview, authorization, and baseline approval.
- Clear, polished evidence presentation.

This is stronger governance engineering than most early products have.

## Critical product flaws

### 1. It does not faithfully replay the customer’s production request

This is the largest flaw.

Both provider adapters transform the configured workflow into a proprietary prompt:

```text
Context:
...

Question:
...

Response requirements:
...
```

See the [OpenAI payload](/home/pedro/Work/silent_regression/lib/silent_regression/spike/providers/open_ai.ex:334) and [Anthropic payload](/home/pedro/Work/silent_regression/lib/silent_regression/spike/providers/anthropic.ex:368).

That means the system is not replaying the exact production call unless the customer’s application already uses this precise structure. It does not support:

- Arbitrary message histories.
- Few-shot user/assistant messages.
- Tool definitions or tool results.
- Multimodal inputs.
- Provider-specific request fields beyond the small allowlist.
- Retrieval, preprocessing, guardrails, or postprocessing from the actual application.
- Prompts assembled by the customer’s deployed code.

Prompt formatting changes model behavior. Consequently, a passing monitor can coexist with a broken production workflow, and a failing monitor can be caused by Silent Regression’s wrapper rather than the provider.

“No SDK” is attractive, but here it creates configuration drift. The customer manually duplicates production behavior into a second system with no mechanism proving the two remain synchronized.

### 2. Contracts cannot express case-specific correctness

The evaluator receives only a contract root and output text:

[contracts/evaluator.ex](/home/pedro/Work/silent_regression/lib/silent_regression/contracts/evaluator.ex:13)

It does not receive the case, expected answer, input variables, context, or case-specific expectations.

Therefore it can verify:

- Output is a valid label—but not that it is the right label for this case.
- JSON has an `amount`—but not that the amount was correctly extracted from this case.
- A citation is present—but not necessarily that it supports the answer.
- A value falls in an allowed set—but not that the selected value is correct.

This seriously weakens the advertised classification, extraction, and RAG use cases. A classifier returning `"approved"` for every input can pass an “allowed labels” contract.

The product needs expectations attached to cases: expected labels, paths and values, allowed alternatives, source IDs, numeric tolerances, and abstention requirements. Evaluation should receive both observation and case expectation.

### 3. The baseline is mostly ceremonial for content regression

Content alerts are generated directly from contract failures. Baseline observations do not participate in content comparison. Baseline-relative behavior currently covers latency and token usage, as seen in [policy.ex](/home/pedro/Work/silent_regression/lib/silent_regression/run_results/policy.ex:212).

So the baseline:

- Proves a provider could complete the workflow once.
- Pins provenance.
- Supplies simple operational reference values.
- Does not establish a content distribution.
- Does not detect content change when both outputs pass the contract.
- Does not improve case-specific correctness.

That is a lot of capture, review, and approval ceremony for limited marginal value. With one sample per case by default, it also says little about stochastic reliability.

Either simplify deterministic monitors so they do not require a baseline, or make the baseline meaningful through repeated sampling and explicit comparison evidence.

### 4. Alert behavior will create noise rapidly

Every failed observation creates a separate contract alert, and alert identity includes the run ID:

- [One finding per failed evaluation](/home/pedro/Work/silent_regression/lib/silent_regression/run_results/policy.ex:59)
- [Run-specific identity](/home/pedro/Work/silent_regression/lib/silent_regression/run_results/policy.ex:411)

If 20 cases fail the same rule, the run can create 20 alerts. If it fails again tomorrow, it creates 20 more. Email delivery is also prepared per alert and recipient.

The system needs incident aggregation:

- Group by monitor, contract version, rule, and failure signature.
- Attach successive runs and affected cases to the existing incident.
- Notify once, then send bounded updates.
- Automatically suppress repeated unchanged failures.
- Provide “first seen,” “last seen,” and recovery state.

Without this, the evidence model becomes operationally exhausting.

## Contract-authoring gaps

### Proof requirements are too weak

Approval requires at least one passing fixture and one failing fixture, not negative coverage for every rule. See [approval_readiness/2](/home/pedro/Work/silent_regression/lib/silent_regression/contract_authoring.ex:325).

A ten-rule contract can be approved with:

- One fixture where everything passes.
- One fixture that challenges only one rule.

The other nine rules have never been shown to reject a relevant bad output.

Approval should require rule-level coverage, with exceptions explicitly waived by the owner.

### UI authoring is less capable than the engine

The general parser supports `all`, `any`, and `not`, but product authoring forces one flat `all` root and rejects nested composites. See [draft_input.ex](/home/pedro/Work/silent_regression/lib/silent_regression/contract_authoring/draft_input.ex:67).

The backend also understands warning severity, but the React authoring UI provides no severity control, effectively making normal user rules critical.

### Marketing demonstrates unsupported behavior

The homepage claims “every factual claim cites source IDs” and displays `claims[*].source_ids` as exact evidence:

[home.html.heex](/home/pedro/Work/silent_regression/lib/silent_regression_web/controllers/page_html/home.html.heex:83)

The evaluator uses exact JSON Pointer paths and does not support wildcard array traversal. Its text citation rule checks declared fact alternatives, not every factual claim.

That mockup should be changed immediately because it overstates concrete evaluator capability.

## UX and adoption problems

The application is polished, but the activation path is demanding:

1. Trust the service with a provider credential.
2. Recreate the production prompt and configuration.
3. Construct representative cases.
4. Learn a low-level contract language.
5. Produce positive and negative outputs.
6. Judge individual rule outcomes.
7. Authorize paid baseline calls.
8. Review and approve the baseline.
9. Configure scheduling.

This creates a buyer paradox:

- Teams capable of authoring these contracts may already have CI evaluation infrastructure.
- Teams attracted to a no-SDK product may struggle with JSON Pointers, stable rule IDs, fixtures, provenance, and evaluator semantics.

A guided case table with expected outcomes would offer much more value than exposing contract-engine primitives first.

Other adoption gaps include:

- No canned demo or safe sandbox before providing a real credential.
- No currency-level cost estimate or budget.
- Only email and in-app notifications.
- No import from existing eval datasets.
- No way to synchronize configuration from production.
- No API or customer-endpoint monitor.
- Static, rapidly aging provider/model capability lists.

## Security and operational gaps

For a service storing prompts, outputs, and provider credentials:

- There is no MFA.
- Credential rotation/revocation, run authorization, and workspace deletion are not protected by recent reauthentication.
- Workspace purging is an operator Mix task rather than an automated, monitored lifecycle.
- Backup deletion is documented rather than technically enforced.
- Production health checks, queue monitoring, restore testing, and deployment rollback remain incomplete.
- Owner/member is a coarse permission model once multiple customer teams use a workspace.

These are reasonable alpha omissions, but credential-bearing external pilots should treat MFA/reauthentication and automated deletion as higher priority than additional UI polish.

## Engineering gaps

The code is carefully tested, but the reproducibility story currently has holes:

- Frontend checks pass: 44/44 tests plus TypeScript.
- Backend currently passes 595/597 tests.
- The two failures depend on ignored files under `results/drift_spike`, referenced by a committed freeze manifest. A clean checkout cannot reproduce the claimed full suite.
- `mix precommit` does not run TypeScript, frontend tests, or the production asset build; see [mix.exs](/home/pedro/Work/silent_regression/mix.exs:82).
- There is no committed CI workflow or repeatable browser E2E suite.
- Elixir/Erlang/Node versions are not pinned.
- Product completion adapters still depend on `SilentRegression.Spike` provider types and implementations.
- Several core contexts and React pages are very large, making future changes risky.
- Run history is limited to 25 and alerts to 100 without pagination.

## Recommended priority order

1. **Fix request fidelity.** Support exact provider-native message payloads or monitor a customer-owned HTTP endpoint. Stop adding prompt wrappers silently.
2. **Make contracts case-aware.** Store expected outcomes on each case and evaluate output against those expectations.
3. **Correct the marketing claims.** Remove the unsupported wildcard/every-claim example.
4. **Redesign alert aggregation.** One incident per persistent failure signature, not one alert per failed observation per run.
5. **Decide what baseline means.** Remove it from purely deterministic monitoring or give it statistically meaningful comparison behavior.
6. **Strengthen contract proof.** Require negative coverage per rule, add severity controls, and show coverage explicitly.
7. **Add a credential-free demo/import path.**
8. **Harden external-pilot security.** MFA or recent reauthentication, automated purge, production observability, and restore verification.
9. **Fix reproducibility.** Commit safe test artifacts or isolate artifact-dependent spike tests, add CI/E2E, include frontend checks in `mix precommit`, and pin the toolchain.
10. **Decouple product provider clients from the spike namespace.**

The best near-term positioning is not “general LLM regression monitoring.” It is:

> Scheduled deterministic conformance testing for a narrowly defined provider request.

That is defensible today. Once exact request fidelity and case-specific expectations exist, the broader product promise becomes substantially stronger.
