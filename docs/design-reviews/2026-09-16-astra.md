## Overall assessment

The product has a defensible narrow purpose: repeatedly exercise a customer's fixed LLM examples and report violations of explicit requirements with inspectable evidence. It has unusually substantial evidence preservation, bounded execution, tenancy, and human review machinery for a private alpha. Choosing deterministic contracts instead of a poorly validated quality score is sound.

The most consequential gaps are now in the continuity of the monitoring loop: preserving the real request being monitored, recovering after credentials or capacity change, and helping customers maintain their monitor after setup. These are more urgent than another provider, semantic scoring, billing, or visual polish. An application can execute its happy path correctly while becoming unusable during an ordinary credential rotation.

The plan appropriately calls the alpha a learning instrument and excludes unconstrained quality monitoring ([plans/private_alpha_implementation_plan.md:34](../../plans/private_alpha_implementation_plan.md#L34)). This review judges it against that small promise, not against a mature observability platform.

## 1. High priority: replay changes the customer's request

**Confirmed implementation.** Product execution delegates to a spike adapter after converting the request into `Spike.Case`. Empty context becomes the literal sentence `No frozen context was supplied.` Both provider adapters then construct a user message with `Context:`, `Question:`, and `Response requirements:` sections. The latter contains the encoded response-format configuration. See [completion_adapter.ex:102](../../lib/silent_regression/providers/completion_adapter.ex#L102), [open_ai.ex:358](../../lib/silent_regression/spike/providers/open_ai.ex#L358), and [anthropic.ex:386](../../lib/silent_regression/spike/providers/anthropic.ex#L386).

**Impact.** A customer can copy their production prompt faithfully and still test a different message. Added instructions and formatting can change classification, extraction, abstention, or citation behavior. A passing replay therefore establishes the behavior of this application's constructed request, not necessarily the workflow the customer believes they supplied. Immutable fingerprints preserve reproducibility of the local experiment; they cannot establish fidelity to production.

**Recommendation.** Make the exact provider-visible request a first-class, previewable artifact. Preserve customer-authored message content by default, or require explicit acceptance of a versioned wrapper. Add payload-level tests that start from user setup and compare the final request body. Test this with a real partner's existing request before treating their monitor as activated. The product's continued dependency on spike transport is a maintenance concern here because experimental prompt construction has become product behavior.

## 2. High priority: routine credential rotation breaks the monitor's attachment

**Confirmed implementation; resulting recovery gap inferred across the call paths.** Rotation supersedes the existing credential and inserts a successor but does not update monitor references ([provider_credentials.ex:102](../../lib/silent_regression/provider_credentials.ex#L102)). The monitor's credential is attached during setup completion ([monitor_setups.ex:213](../../lib/silent_regression/monitor_setups.ex#L213)); subsequent setup changes reject completed setups ([monitor_setups.ex:278](../../lib/silent_regression/monitor_setups.ex#L278)). Execution eligibility requires the credential attached to the monitor to be valid ([monitor_operations.ex:412](../../lib/silent_regression/monitor_operations.ex#L412)). I found no authenticated route to replace that attachment after completion ([router.ex:54](../../lib/silent_regression_web/router.ex#L54)).

**Impact.** Validating the replacement credential does not make the existing monitor use it. An ordinary security operation can strand a working monitor and require operator intervention or recreation. The credential screen's instruction to validate the replacement is incomplete as recovery guidance.

**Recommendation.** Provide an owner-controlled replacement operation that shows affected monitors, validates the successor for their requested models, and updates future execution references without rewriting historical run credentials. Explicitly decide whether replacement changes baseline compatibility. Verify rotation → validation → existing monitor resume → bounded run with fake providers. This is a more important release test than repeating setup from scratch.

## 3. High priority: the authentication circuit breaker has no ordinary reset path

**Confirmed predicate; recovery failure inferred from public operations.** `repeated_authentication_failures?/1` examines the latest terminal manual/scheduled runs and continues returning true while those runs contain authentication or authorization failures ([monitor_operations.ex:431](../../lib/silent_regression/monitor_operations.ex#L431)). `ensure_eligible/4` rejects that state, and configure, resume, and Run now all call it ([monitor_operations.ex:394](../../lib/silent_regression/monitor_operations.ex#L394), [monitor_operations.ex:206](../../lib/silent_regression/monitor_operations.ex#L206)). Credential validation does not replace these historical run outcomes.

**Impact.** Even if a provider fixes an account permission or billing issue without changing the key, the monitor cannot produce a successful run that would clear its own failure history. This is a state-machine dead end, separate from credential replacement.

**Recommendation.** Store a breaker epoch or reset event, and permit a deliberately authorized probe after successful credential/model validation. Preserve the old failure evidence while evaluating consecutive failures only since recovery. Add a test that trips the breaker, fixes the fake provider, and resumes the same monitor through public context/controller operations.

The existing test verifies that two authentication failures cause a pause; it stops at that assertion ([monitor_operations_test.exs:248](../../test/silent_regression/monitor_operations_test.exs#L248)). It establishes the safety transition, not the recovery lifecycle.

## 4. High priority: a temporary quota limit can silently become permanent loss of coverage

**Confirmed implementation.** Scheduled eligibility includes current workspace capacity. Failure auto-pauses the monitor and clears `next_run_at` ([monitor_operations.ex:327](../../lib/silent_regression/monitor_operations.ex#L327), [monitor_operations.ex:503](../../lib/silent_regression/monitor_operations.ex#L503)). Capacity resets are exposed as a UTC boundary, but no automatic resume is part of this path. Run-limit exhaustion returns `:workspace_run_limit` ([pilot_policies.ex:61](../../lib/silent_regression/pilot_policies.ex#L61)), which is not explicitly mapped by `pause_reason/1` and becomes `:incompatible_configuration` ([monitor_operations.ex:583](../../lib/silent_regression/monitor_operations.ex#L583)).

The auto-pause path records an audit event. The implemented email outbox is driven by result alerts ([notifications.ex:49](../../lib/silent_regression/notifications.ex#L49)); a refusal before run creation produces no result alert through that mechanism.

**Impact.** A manual or baseline run can consume capacity, cause another monitor to pause, and leave it stopped after capacity resets. The user must discover this in the app. A run cap can additionally be explained as the wrong problem. For a product intended to detect silent failures, silent loss of its own coverage is particularly damaging.

**Recommendation.** Distinguish waiting for capacity from a persistent safety pause. Show the next retry time and last successful check, alert owners when coverage stops, and map every capacity error accurately. Add a fake-provider test spanning quota exhaustion and the next UTC day. Longer term, monitor scheduler heartbeat and overdue runs independently of result production.

## 5. High priority for pilot learning: configuration is versioned internally but effectively one-shot in the product

**Confirmed product boundary.** Completed setup is locked in both the UI and domain ([Setup.tsx:875](../../assets/js/pages/Monitors/Setup.tsx#L875), [monitor_setups.ex:278](../../lib/silent_regression/monitor_setups.ex#L278)). Domain functions create and activate monitor versions ([monitors.ex:114](../../lib/silent_regression/monitors.ex#L114)), but the router exposes setup and contract revision rather than a successor workflow configuration flow ([router.ex:59](../../lib/silent_regression_web/router.ex#L59)).

**Impact.** The partner can revise a rule after a false alert, but cannot comparably revise the prompt, cases, frozen context, or model through the existing product workflow. Those are ordinary changes during a pilot, especially when a missed regression reveals an absent case. Recreating the monitor fragments history and adds baseline/setup work. The feedback loop is biased toward changing the checker because that is the correction the application makes convenient.

**Recommendation.** Add “Create next configuration version” from the existing monitor: copy the current configuration, edit a draft, disclose baseline invalidation, and activate deliberately. Preserve history and link the new version to the motivating review. Do not loosen immutable evidence to make editing possible.

## 6. Medium priority: alerts represent failed observations, not enduring incidents

**Confirmed policy.** Each failed evaluation becomes a finding with a run-specific identity ([policy.ex:59](../../lib/silent_regression/run_results/policy.ex#L59), [policy.ex:411](../../lib/silent_regression/run_results/policy.ex#L411)). Every new alert prepares a delivery for each eligible member ([notifications.ex:49](../../lib/silent_regression/notifications.ex#L49)). Deduplication protects against retrying the same alert; it does not group the same rule/case problem across runs. The workspace list is capped at 100 without pagination in that function ([run_results.ex:23](../../lib/silent_regression/run_results.ex#L23)).

**Impact.** A persistent failure in ten cases can produce ten alerts per run and ten emails per subscribed member. Repetition expands the review queue even when the team already understands the problem. Older unresolved alerts can fall outside the visible list. Exceptionally accepted baseline failures remain subject to the same absolute contract-failure policy: approval does not teach alerting to suppress those known failures ([health.ex:89](../../lib/silent_regression/baselines/health.ex#L89)).

**Recommendation.** Preserve observation-level evidence but group action items by monitor, case, rule, and relevant configuration. Send a run/incident summary, distinguish recurrence from new failure, and expose pagination/counts. State explicitly what exceptional baseline acceptance does to future alerts. Validate expected email volume with a deliberately broad failure before external onboarding.

## 7. Product risk: a proven rule is not necessarily a useful detector

**Confirmed limits, not a demand to add semantic judging.** Approval requires passing and failing fixtures and their expected results ([contract_authoring.ex:325](../../lib/silent_regression/contract_authoring.ex#L325)). Citation attribution checks literal text near an allowed citation ([citations.ex:24](../../lib/silent_regression/contracts/citations.ex#L24)). The templates candidly disclose syntactic citation checks and inability to understand paraphrases or contradictions ([templates.ex:53](../../lib/silent_regression/contract_authoring/templates.ex#L53)). These are appropriate boundaries.

**Remaining hypothesis to test.** Customers may struggle to express their consequential failures using these rules, or may approve a rule that detects the supplied negative example but misses realistic mistakes. A schema-valid extraction can contain the wrong answer. A nearby permitted citation is not proof that a claim follows from the source. One positive and one negative fixture do not establish coverage of every leaf or every case.

**Recommendation.** Start with the most objectively checkable use case, such as a known-label routing task or extraction with case-specific expected values. Ask partners for genuine past failures before authoring rules; reserve some as unseen examples. Show an explicit coverage checklist and untested rule branches. Evaluate false alerts and missed regressions on those examples before expanding into broadly described grounded-answer monitoring.

## 8. Product interpretation: baseline and sampling need a clearer customer explanation

**Confirmed implementation.** Contract failures are absolute; the baseline contributes provenance and operational comparisons, not a subtraction of baseline contract failures ([policy.ex:38](../../lib/silent_regression/run_results/policy.ex#L38)). Scheduled/manual operation hardcodes one sample per active case ([monitor_operations.ex:531](../../lib/silent_regression/monitor_operations.ex#L531)).

**Impact.** “Baseline” can imply that the product establishes normal output variability and detects a statistically meaningful change. This implementation instead asks whether today's sampled outputs meet rules, plus conservative latency/token thresholds. It can detect violations without proving that their probability increased. Illustratively, if a case has an independent 5% failure probability, one daily sample has only about a 30% chance of seeing at least one failure in a week (`1 - 0.95^7`). This is arithmetic illustrating a limitation, not an estimated property of any provider.

**Recommendation.** Explain the distinct jobs of rule approval, baseline capture, and recurring samples. Label results as sampled contract evidence, not universal health. If a partner needs rare-event detection, negotiate cases, cadence, and sample counts together with budget instead of implying that a single daily pass provides strong assurance.

## 9. Medium priority: retained history makes contract approval increasingly expensive

**Confirmed implementation; performance impact not benchmarked.** Contract approval holds a transaction and monitor lock while rescoring history ([contract_authoring.ex:230](../../lib/silent_regression/contract_authoring.ex#L230)). The rescorer loads every successful observation for the monitor with `Repo.all()` and evaluates them sequentially ([rescorer.ex:17](../../lib/silent_regression/contract_authoring/rescorer.ex#L17)). Active workspaces retain raw evidence for their lifetime ([DATA_RETENTION.md](../pilot-readiness/DATA_RETENTION.md)).

**Impact.** Initial demos remain small, but the cost of an ordinary correction grows with all previous runs. Approval can hold locks and request resources longer precisely for the customers who use the product most. This is a growth risk, not a measured current outage.

**Recommendation.** Move historical rescore into bounded durable batches, show progress, and atomically activate only after completion. Pin the observation set or a cutoff so newly arriving runs cannot make completion ambiguous. Measure approval time against a realistic month of pilot usage before needing this change urgently.

## 10. Operational and commercial readiness are separate from local completeness

The deployment checklist correctly leaves production database controls, restore testing, mail deliverability, queue alerting, and named operational ownership unchecked ([DEPLOYMENT_CHECKLIST.md:5](../pilot-readiness/DEPLOYMENT_CHECKLIST.md#L5)). The restore procedure requires reconciliation with an authoritative post-backup deletion record ([BACKUP_RESTORE.md:15](../pilot-readiness/BACKUP_RESTORE.md#L15)); the deployment needs to make the location and durability of that record concrete. Documentation alone does not prove restoration or deletion after recovery.

The standard telemetry module currently defines request/database/VM measurements, with no configured reporter there ([telemetry.ex:11](../../lib/silent_regression_web/telemetry.ex#L11)). Before a hosted pilot, name owners and demonstrate monitoring for overdue schedules, unknown capture outcomes, undelivered notifications, and purge deadlines. A failed result can alert itself; a stopped scheduler cannot.

Call caps are useful and enforced centrally, but they are not currency budgets: they reserve maximum call counts, including possible retries ([pilot_policies.ex:70](../../lib/silent_regression/pilot_policies.ex#L70)). Token sizes and model prices vary. Keep UI language precise, show a conservative cost estimate or explicitly say it is unavailable, and explain that reserved capacity need not equal actual calls.

The pilot should also test whether the outcome warrants the setup and review effort. Activation analytics measures time to schedule activation and assistance ([product_analytics.ex:102](../../lib/silent_regression/product_analytics.ex#L102)); successful activation does not establish useful detection or willingness to pay. Record partner-level evidence of a consequential issue detected, review time saved or spent, false-alert burden, cases the contract could not express, and continued use without founder prompting. Absence of billing is appropriate at this stage.

## Recommended order

1. Repair request fidelity, credential replacement, and circuit-breaker recovery; prove each through a full lifecycle test.
2. Make lost monitoring coverage visible and recover correctly from temporary quota exhaustion.
3. Expose successor configuration editing, then exercise a missed-regression review that adds a case and resumes monitoring.
4. Run a small partner exercise on a tightly defined use case, with real historical failures and measured alert/review burden.
5. Complete deployment and recovery drills before hosting that pilot. Address alert grouping and rescore scaling according to the exercised workload.

Keep the sound foundations: server-owned tenancy and authorization, explicit spend authorization, immutable evidence, operational failures separated from content claims, and human review linked to the exact evaluated version. The goal is to make that evidence trustworthy and the monitoring loop recoverable, rather than to broaden the product before its core lifecycle works reliably.
